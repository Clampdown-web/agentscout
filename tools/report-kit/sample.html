Summary Sample

What this means for you

You can rely on this server for everyday use. It is a public Microsoft service, and every documentation search, page fetch, and code-sample lookup we ran came back successfully.

It is fast, too: connecting and every request finished in well under a second.

What holds the score at 90, not 100, is incomplete self-description. The server says it offers extra menus (prompts and resources), but both lists were empty, and two of the tool definitions are missing small but important details.

Make the three fixes listed on the cover, then book a free retest so we can show the score improving.

Verdict

Microsoft Learn MCP is a strong, public, first-party server. It negotiates protocol 2025-06-18, issues a session, lists three well-described read-only tools, and returned useful documentation and code samples on every call, in well under a second. The daily AgentScout HTTP reachability check already had this listing as live (homepage and GitHub both HTTP 200, checked November 10, 2026, 7:03 AM PT).

The score is not 100. The server advertises prompts and resources, then returns empty lists for both. microsoft_docs_search does not mark its query argument as required. microsoft_docs_fetch has no outputSchema, unlike the other two tools. serverInfo is only a name and version. Those are fixable.

Top fixes Sample

Top 3 fixes

These are the changes that would close the largest remaining gaps in the score. Each one is a schema or capability change — no behavior change is required for the tools that already work.

1

Mark query as required on microsoft_docs_search, and remove "default": null.

The property exists and is well described, but it is omitted from required and is given "default": null. A client can legally call the tool with no query. The other two tools correctly require their main argument. This is a one-line schema change that prevents empty searches.

  1. Open the inputSchema for microsoft_docs_search.
  2. Add query to the required array, matching microsoft_code_sample_search and microsoft_docs_fetch.
  3. Remove "default": null from the query property.
  4. Redeploy and confirm that a call with no query is rejected.
2

Stop advertising empty surfaces — or fill them.

initialize capabilities include prompts.listChanged and resources.listChanged, but prompts/list and resources/list both returned empty arrays with HTTP 200. Clients may offer empty menus, or assume list-changed notifications that never matter.

  1. Decide whether prompts and resources are in scope for this server.
  2. Option A — fill them: add one or two prompts that wrap the documented workflow (for example “Search Microsoft docs” and “Fetch a Learn page”), and/or a resource template for Learn URLs.
  3. Option B — be honest: omit prompts and resources from initialize capabilities until there is something to list.
  4. Redeploy and confirm that prompts/list and resources/list match the advertised capabilities.
3

Add outputSchema to microsoft_docs_fetch, and enrich serverInfo.

Search and code-sample search both declare an outputSchema. Fetch is the tool that returns the largest body, and it only has unstructured content. serverInfo is only a name and version. A small metadata change makes this clearer for registries, catalogs, and typed clients.

  1. Declare an outputSchema on microsoft_docs_fetch (for example Markdown text plus the canonical URL).
  2. Add title, websiteUrl, and a one-line description to serverInfo. A website URL here should be https://learn.microsoft.com/ (or the GitHub repo).
  3. Optional: add icons so MCP client UIs can display the server consistently.
  4. Redeploy and confirm typed clients can validate the fetch result.

Also worth fixing

These two items did not cost as many points as the top three fixes. They are still worth fixing.

  1. serverInfo is thin. Only name and version. Context7, by comparison, also returns title, websiteUrl, and description on initialize. Optional icons would help MCP client UIs.
  2. Search results are double-encoded as text. The content[0].text value is a JSON string of the same results already present in structuredContent. Harmless, but messier for clients that only read text content.

How this was tested

  1. Reused AgentScout's existing daily MCP reachability result (HTTP HEAD-then-GET of the listed website and GitHub URL — this does not speak MCP).
  2. Connected for real over Streamable HTTP: JSON-RPC initialize, then notifications/initialized, then tools/list, resources/list, and prompts/list.
  3. Called three safe, read-only tools with harmless documentation queries. No write, send, pay, or delete tools were present or called.
  4. Repeated initialize and the same three tool calls for five runs and took the median (p50) latency.
  5. Linted tool schemas (descriptions, required fields, types, annotations).

Client: agentscout-mcp-test-sample 0.1.0. User-Agent: AgentScoutMCPTest/0.1 (+https://agentscouthq.com/about.html). Raw JSON-RPC transcript (all five runs, including full tool-call bodies) is the source of every latency number and schema claim in this report.

Reproducible commands

These speak MCP. They do not submit anything, and they only read documentation.

# initialize (expect HTTP 200, text/event-stream, mcp-session-id)
curl -sS -D - -o /tmp/mslearn-init.sse \
  -X POST 'https://learn.microsoft.com/api/mcp' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'Content-Type: application/json' \
  -H 'MCP-Protocol-Version: 2025-06-18' \
  -H 'User-Agent: AgentScoutMCPTest/0.1 (+https://agentscouthq.com/about.html)' \
  --data '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"agentscout-mcp-test-sample","version":"0.1.0"}}}'

# Then: notifications/initialized (send the session header from step 1),
